# 기술적 한계와 남은 검증

## 이 시험장의 범위

- 실제 금융기관·실제 계좌·개인정보를 사용하지 않는 가상 시험장이다. 금융 규제 적합성, 운영 은행 수준의 안전성·가용성은 주장하지 않는다.
- `llooggeerr` eBPF 수집기를 구현하거나 연동 완료한 결과물이 아니다. 모의 수신기의 commit·중복 결과는 수집기의 수집 정확도나 보존율을 뜻하지 않는다.
- 기존 프로젝트의 코드는 복사하지 않는다. 중요도 정책, 중앙 구조 A/B/C, 문자열 상한, 성능 합격 수치 등 기획서의 미정 사항은 여기서 최종 확정하지 않는다.

## Docker와 Linux

컨테이너는 호스트의 Linux 커널을 공유한다. 컨테이너별 프로세스·네트워크·파일 namespace와 cgroup을 구분할 수 있지만 각각 독립 커널을 가진 서버가 아니다. Docker 관리자 권한으로 네트워크·마운트를 바꿀 수 있다. 동일 브리지의 통신은 기본적으로 양방향이며 이 배치는 물리 망 분리가 아니다.

호스트 loopback 웹 포트 게시용 `web-entry`는 `internal: true`가 아니며 `web`만 연결된다. 이 컨테이너에는 외부 송신 경로가 생길 수 있다. 시험 코드는 고정된 내부 API만 호출하지만 웹 컨테이너 자체의 외부 통신까지 Docker 설정만으로 차단하지는 않는다. 외부 송신 금지가 필요한 배포에서는 호스트 방화벽 정책을 별도 적용·검증해야 한다. 다른 고객·직원·업무·DB·로그 네트워크는 내부망으로 유지한다.

Windows에서 실행하는 경우 관측 대상은 WSL2 또는 Docker Desktop의 Linux VM이다. Windows 커널 이벤트를 Linux eBPF로 수집한다고 표현하지 않는다. WSL 배포판과 Docker Desktop 데몬은 서로 다른 실행 환경일 수 있으므로 실제 Docker context·커널·메모리 한도를 결과에 함께 기록한다.

eBPF는 호스트 또는 별도 관측 전용 구성에서 검토한다. 커널 기능·BTF·tracepoint·capability 조건은 설치 호스트마다 확인해야 한다. 업무 컨테이너 전체에 privileged를 주거나 Docker socket을 배포하는 방식으로 해결하지 않는다. 컨테이너 이름은 커널 필드가 아니므로 런타임 메타데이터와 수명·cgroup·namespace를 연결해야 한다.

부팅·전원 차단·커널 패닉·호스트 OOM은 이 은행망 안에서 재현하지 않는다. 이러한 실험에는 별도의 폐기 가능한 VM과 복구 절차가 필요하다. 컨테이너 메모리 한도 내 OOM과 호스트 전체 OOM은 다른 사건이다.

## 저장과 내구성

PostgreSQL 트랜잭션과 수신기 SQLite commit은 각 DB가 제공하는 저장 완료 경계를 사용한다. 컨테이너 재시작 이후 데이터가 유지되는지 시험할 수 있지만 디스크 장치 전원 손실, 파일시스템·하이퍼바이저 캐시, 저장 장치 고장에 대한 무손실을 증명하지 않는다.

HTTP 성공, 메시지 수신, 저장 완료는 별도 상태다. 수신기의 `write_failure`는 실패 처리 경로를 시험하는 모의 장애다. 실제 ENOSPC는 `events` 서비스의 크기가 제한된 tmpfs에서 따로 발생시키므로 호스트 파일시스템을 가득 채우지 않는다. tmpfs ENOSPC는 실제 영속 블록 장치의 고장 모델을 모두 대신하지 않는다.

## 인증과 관리

개발용 비밀은 자동 생성하여 소스 밖에 보관하지만 운영용 KMS·TLS·인증서 회전·다중 요소 인증을 구현한 시스템은 아니다. 내부 서비스 키 공유와 HTTP는 고립된 시험장에 한정한다. 직원 역할을 제한하고 계좌 소유권을 별도로 검사한다. 임의 셸 명령·임의 외부 목적지·임의 호스트 경로를 받는 API는 제공하지 않는다.

현재 DB 초기화와 계정계 실행은 같은 개발용 `bank` DB 역할을 사용하며, PostgreSQL 공식 초기화로 만들어지는 이 역할에는 관리자 권한이 있다. 역할별 애플리케이션 권한 검사와 DB 엔진의 최소 권한 모델은 별개다. 실운영 수준의 DB 권한 분리로 표현하지 않으며, 해당 강화가 필요하면 초기화 전용 주체와 제한된 실행 계정을 나누어야 한다.

Docker stdout 로그는 용량이 제한된 서비스 진단 스트림이며 순환된다. 독립 검증 정답과 모의 수신 서버가 수락한 원본은 별도 영속 저장하고 샘플링하지 않는다. 향후 stdout까지 수집 원본으로 지정한다면 진단 스트림의 순환 설정을 그대로 원본 보존 정책으로 사용하지 말고, 원본 영속 보관 경로를 먼저 연결해야 한다. 현재 설정은 전체 stdout 이력 보존을 보장하지 않는다.

## 정답과 지표

업무 1건이 커널 이벤트 1건인 것은 아니다. syscall 시도, 반환, 애플리케이션 성공, DB commit은 서로 다른 관측 경계다. 매칭 조건에 맞지 않는 정답은 임의로 누락 또는 성공으로 집계하지 않는다. 정상·비정상 레이블은 시험 입력일 뿐 공격 판정 기능이 아니다.

CPU·메모리·I/O 샘플은 계측 간격 사이의 피크를 놓칠 수 있다. 여러 컨테이너는 동일 호스트 자원을 경쟁한다. 목표 RPS를 달성하지 못한 실험만으로 수집기 성능 상한을 단정하지 않는다. 수집기 미연동 지표는 null과 사유로 표시하며 0을 측정값처럼 쓰지 않는다.

## 후속 작업

1. 실제 Linux 관측 호스트에서 커널·BTF·권한·지원 이벤트를 확인한다.
2. 수집기의 독립 스키마와 운영 정책이 확정되면 시험장의 연결 어댑터를 작성한다.
3. 원본·수집 실패·저장 실패·미확정 구간을 구분하는 매칭 규칙을 실제 수집 결과로 검증한다.
4. 같은 조건의 수집기 미실행/실행 실험을 반복하고 서비스 지연·실제 처리량·보존율을 비교한다.
5. 예비실험 이후 성능 합격 기준을 별도 확정한다.
6. 장시간·극단 부하와 독립 VM 장애 시험은 자원 한도와 복구 절차를 확인한 별도 실행으로 수행한다.

실제 실행 여부와 통과/실패는 README 및 저장된 결과 파일에 구분하여 기록한다. 구현된 테스트가 존재한다는 사실만으로 그 테스트를 실행·통과했다고 간주하지 않는다.
