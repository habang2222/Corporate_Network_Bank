# 보안 기록 인터페이스

`security` 서비스는 HTTP `POST /events`로 구조화 이벤트를 받아 SQLite에 저장합니다. 보안 기록은 공격을 차단하거나 자동 판정하기 위한 기능이 아니라 사후 조사의 데이터 출처입니다.

필수 필드:

```json
{
  "event_id": "unique-id",
  "source": "application",
  "service": "new-service",
  "event": "business_action",
  "time_ns": 1700000000000000000
}
```

`event_id`는 재전송 때 같은 값을 유지합니다. 같은 ID·같은 내용의 중복은 저장된 ID를 반환하고, 같은 ID·다른 내용은 409를 반환합니다. 추가 필드에는 사용자명, 요청 ID, 대상 객체, 결과, 크기·해시 등을 넣을 수 있습니다. 비밀번호·세션 토큰·민감한 거래 본문은 넣지 않습니다.

`X-Service-Key` 헤더는 `bootstrap`이 최초 구동 때 생성한 개발용 키입니다. 이벤트 쓰기와 조회 모두 내부망과 이 키가 필요합니다. 조회는 `GET /events?after_id=0&limit=100`으로 하며 최대 500건씩 순서대로 가져올 수 있습니다.

각 업무 서비스는 같은 이벤트를 stdout에도 JSON 한 줄로 출력합니다. 중앙 전송 오류는 `audit_delivery` 기록으로 출력됩니다. 계정계는 허용된 조회의 대상·행 수를 업무 감사에 남기고, 방화벽은 전달한 응답의 바이트 수를 남깁니다. 보안 서비스의 저장 성공과 원래 업무의 성공은 별개입니다. 조사자는 `time_ns`와 보안 서비스의 `received_ns`를 분리하고, core의 DB 확정 기록과 대조해야 합니다.

다른 프로젝트에서 재사용하려면 새 서비스와 `security`를 같은 내부 업무망에 연결하거나 새 전용 감사망을 추가합니다. 새 서비스는 위 형식과 키로 전송하며, 외부 분석기는 서비스별 stdout과 중앙 조회 결과를 함께 읽을 수 있습니다.
